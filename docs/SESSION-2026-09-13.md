## alpha.7 — FML runtime bridge

A dedicated runtime codec exists for the legacy `FML` runtime channel, separate from `FML|HS`.

```text
0 = CompleteHandshake
1 = OpenGui
2 = EntitySpawnMessage
3 = EntityAdjustMessage
```

`EntityAdjustMessage` keeps original Forge semantics and updates the packet-position baseline rather than teleporting the entity:

```text
serverPosX / 32.0
serverPosY / 32.0
serverPosZ / 32.0
→ Entity.syncPacketPositionCodec(x, y, z)
```

Live testing confirmed real PLAY `EntityAdjustMessage` packets are decoded and applied successfully.

## Skin ownership conclusion

```text
LegacyForgeBridge does NOT own:

```

## Why legacy server messages became English

Forge/Minecraft 1.7.10 sends translatable message keys such as:

```text
commands.help.header
commands.help.footer
commands.achievement.usage
```

The server does not pre-localize those original vanilla messages to Chinese.

ViaVersion rewrites translation components while crossing protocol boundaries. In particular, the 1.12.2→1.13 mapping contains removed legacy keys with English inline fallback values, for example:

```text
-commands.help.header=--- Showing help page %s of %s (/help <page>) ---
```

Without LFB intervention, Via replaces the old key before the 1.21.11 client language system can resolve the original 1.7.10 translation.

## alpha.10 — legacy message translation preservation

### Design rule

Do **not** reverse-match Via's final English sentence back into a key.

While ViaFabricPlus targets Minecraft 1.7.6-1.7.10:

```text
1.7.10 server component
translate = original legacy message key
        ↓
ViaVersion performs normal component/protocol conversion
        ↓
LFB restores the selected original message key after each Via component rewriter
        ↓
1.21.11 TranslatableContents
        ↓
LFB maps the preserved key to a collision-free alias translation
        ↓
Minecraft's selected language stack (zh_tw / en_us)
```

ViaVersion still owns component shape conversion, nested arguments, hover/click data, NBT representation and ordinary content-key mapping.

### Message keys only — content names are deliberately excluded

LFB preserves server/message-oriented keys such as:

```text
commands.*
chat.type.*
chat.stream.*
death.*
multiplayer.player.*
multiplayer.disconnect.*
disconnect.*
achievement.*
stat.*
stats.tooltip.*
gameMode.*
```

Plus a small set of old bed-status messages and explicit Forge server-message keys.

The following are deliberately **not** preserved by LFB and continue through ViaVersion + Minecraft 1.21.11 normally:

```text
item.*
ordinary tile.* / block.*
entity.*
container.*
options.*
forge.configgui.*
fml.configgui.*
```

This is an explicit regression requirement: connecting to 1.7.10 must not make modern item/block names consume the old 1.7.10 language table.

Nested content names inside a preserved server message also remain Via-owned. For example, LFB may preserve the outer `commands.give.success` message while a nested item-name component continues through Via's normal item translation path.

### Language resources

The supplied originals are:

```text
minecraft/lang/en_US.lang
minecraft/lang/zh_TW.lang
forge/lang/en_US.lang
forge/lang/zh_TW.lang
```

Only message-oriented entries were retained as build inputs:

```text
assets/lfb-minecraft/legacy-lang/en_us/*.lang
assets/lfb-minecraft/legacy-lang/zh_tw/*.lang
assets/lfb-forge/legacy-lang/en_us/*.lang
assets/lfb-forge/legacy-lang/zh_tw/*.lang
```

Filtered source counts:

```text
Minecraft en_US: 428 message entries
Minecraft zh_TW: 423 message entries
Forge en_US:       9 message entries
Forge zh_TW:       9 message entries
```

At build time `generateLegacyLanguageAliases` converts those filtered `.lang` inputs into normal modern JSON resources:

```text
assets/lfb-minecraft/lang/en_us.json
assets/lfb-minecraft/lang/zh_tw.json
assets/lfb-forge/lang/en_us.json
assets/lfb-forge/lang/zh_tw.json
```

The generated translation keys are collision-free aliases rather than original Minecraft/Forge keys, for example:

```text
lfb.minecraft.commands.help.header
lfb.forge.forge.texture.preload.warning
```

Therefore Minecraft may load these JSON files through its normal language stack without replacing the real 1.21.11 keys globally.

The source `.lang` files are excluded from the final runtime JAR. The build conversion:

- reads UTF-8;
- ignores blank/comment lines;
- splits on the first `=`;
- normalizes legacy numeric `%d/%f` placeholders to `%s`, preserving positional indexes.

### Implementation points

- `ViaComponentTranslationMixin`
  - targets ViaVersion `ComponentRewriterBase`;
  - snapshots only whitelisted legacy message `translate` keys;
  - restores those keys after each JSON/NBT Via component rewrite;
  - leaves item/block/entity/container/UI translation mappings untouched.

- `LegacyTranslationBridge`
  - decides which old keys qualify as message translations;
  - maps preserved Minecraft keys to `lfb.minecraft.<old-key>`;
  - maps preserved Forge keys to `lfb.forge.<old-key>`;
  - falls back to normal modern `Language` behavior when no alias exists or the target is not 1.7.10.

- `TranslatableContentsMixin`
  - redirects only the final `Language.getOrDefault(...)` lookup;
  - lets the normal Minecraft language stack choose `zh_tw`, `en_us`, or its normal fallback order.

## Guardrails

- Keep `FML|HS` handshake and `FML` runtime codecs separate.
- Do not assume modern registry raw IDs equal Forge 1.7.10 numeric IDs.
- Do not globally mutate modern registries or the modern Minecraft language table.
- Do not translate `EntityAdjustMessage` into direct entity teleportation.
- Do not intercept or replace player skin resolution in LegacyForgeBridge.
- Do not reverse-match Via's English strings back into translation keys.
- Preserve only legacy **message** translation keys; do not route item/block/entity/container names through the 1.7.10 catalogue.
- Keep `legacyforgebridge.log` as one file per Minecraft launch.
