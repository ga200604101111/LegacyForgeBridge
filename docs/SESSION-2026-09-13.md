## alpha.7 — FML runtime bridge

A dedicated runtime codec was added for the legacy `FML` channel, separate from `FML|HS`.

Runtime discriminators:

```text
0 = CompleteHandshake
1 = OpenGui
2 = EntitySpawnMessage
3 = EntityAdjustMessage
```

`EntityAdjustMessage` is implemented with original Forge semantics. It updates the modern packet-position baseline instead of teleporting the entity:

```text
serverPosX / 32.0
serverPosY / 32.0
serverPosZ / 32.0
→ Entity.syncPacketPositionCodec(x, y, z)
```

Live testing confirmed many real PLAY `EntityAdjustMessage` packets are decoded and applied successfully. Therefore the remaining issue where only the user's own player appearance looks wrong is not being treated as an EntityAdjust problem.

## Local-player skin conclusion

The Minecraft 1.7.10 source confirms skin loading is client-side:

```text
AbstractClientPlayer
→ client SkinManager
→ MinecraftSessionService.getTextures(...)
→ TextureManager
```

For the local session profile, if texture data is initially empty, 1.7.10 can call `fillProfileProperties(...)` client-side and retry. The server does not send the player's skin PNG as authoritative appearance data.

This matters because the user intends to use a custom skin mod that already replaces/corrects skin resolution.

## alpha.8 — retired approach

`alpha.8` briefly introduced an `AbstractClientPlayer#getSkin()` fallback using Minecraft's authenticated startup profile.

That approach compiled and passed CI, but it is intentionally removed because LegacyForgeBridge should not compete with custom skin mods or take ownership of skin selection.

## alpha.9 — skin-neutral policy

LegacyForgeBridge now has **zero ownership of player skin resolution**.

Removed:

- `AbstractClientPlayer#getSkin()` interception;
- authenticated `profileFuture` accessor;
- local skin fallback policy;
- local skin fallback tests;
- client mixin configuration used only for skin replacement.

Policy:

```text
LegacyForgeBridge owns:
- Forge/FML handshake
- Forge/FML runtime semantics
- legacy registry identity
- converted-mod compatibility

LegacyForgeBridge does NOT own:
- skin downloading
- skin caching
- skin URL resolution
- Steve/Alex/slim selection
- cape skin service behavior
- custom skin mod behavior
```

The bridge should preserve the player's identity/profile data and then allow vanilla Minecraft or an installed custom skin mod to decide how appearance is loaded.

### P2 — FORGE runtime channel

The clean server sends a `FORGE` payload during CONFIGURATION. It is currently logged but not handled. Decode this separately from the `FML` runtime channel.

### P3 — Full modded EntitySpawn

Current runtime support decodes the stable `EntitySpawnMessage` header. Future support needs:

- legacy DataWatcher metadata;
- Forge entity registration identity;
- throwable owner and velocity fields;
- mod-specific additional spawn data.

### P4 — Legacy OpenGui dispatch

`OpenGui` is parsed, but dispatch must be connected to converted-mod GUI identity rather than hard-coded numeric IDs.

### P5 — Legacy translation compatibility

Some removed 1.7.10 translation keys can display in English. Implement a session-only legacy translation fallback; do not globally replace the modern language table.

### P6 — First converted mod regression

After clean Forge runtime behavior is stable, use `RPGTool1-1.1-1.7.10.jar` as the first real converted-mod regression sample.

## Guardrails

- Keep `FML|HS` handshake and `FML` runtime codecs separate.
- Do not assume modern registry raw IDs equal Forge 1.7.10 numeric IDs.
- Do not globally mutate modern registries or language tables.
- Do not translate `EntityAdjustMessage` into direct entity teleportation.
- Do not intercept or replace player skin resolution in LegacyForgeBridge.
- Keep `legacyforgebridge.log` as one file per Minecraft launch.
