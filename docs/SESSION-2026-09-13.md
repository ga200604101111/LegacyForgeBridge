## FML runtime bridge

Handshake (`FML|HS`) and runtime (`FML`) codecs remain separate.

Runtime discriminators:

```text
0 = CompleteHandshake
1 = OpenGui
2 = EntitySpawnMessage
3 = EntityAdjustMessage
```

`EntityAdjustMessage` keeps original Forge semantics and updates the modern packet-position baseline instead of teleporting the entity:

```text
serverPosX / 32.0
serverPosY / 32.0
serverPosZ / 32.0
→ Entity.syncPacketPositionCodec(x, y, z)
```

Live testing previously confirmed real PLAY `EntityAdjustMessage` packets are decoded and applied successfully.

## Skin ownership boundary

LegacyForgeBridge remains skin-neutral.

```text
LegacyForgeBridge owns:
- Forge/FML handshake
- Forge/FML runtime semantics
- legacy registry identity
- converted-mod compatibility

LegacyForgeBridge does NOT own:
- skin downloading/caching
- skin URLs
- Steve/Alex/slim selection
- cape skin-service behavior
- custom skin mod behavior
```

The client now uses CustomSkinLoader independently. If local appearance is still wrong later, inspect UUID/name/profile identity reaching the skin mod; do not reintroduce `getSkin()` interception.

## Legacy message translation architecture

Forge/Minecraft 1.7.10 sends translation keys such as:

```text
commands.help.header
commands.help.footer
commands.achievement.usage
```

ViaVersion may rename old keys or replace removed ones with English inline fallback text while crossing protocol boundaries. LFB must not reverse-match the final English sentence back to a key.

For a 1.7.10 target, the intended flow is:

```text
1.7.10 server component
translate = original legacy message key
        ↓
ViaVersion performs normal component/protocol conversion
        ↓
LFB restores selected original message key
        ↓
1.21.11 TranslatableContents
        ↓
LFB collision-free alias translation
        ↓
Minecraft selected language stack (zh_tw / en_us)
```

Only message-oriented translations are preserved, including:

```text
commands.*
chat.type.*
chat.stream.*
death.*
multiplayer.player.*
multiplayer.disconnect.*
disconnect.*
achievement.*
stat.*
stats.tooltip.*
gameMode.*
```

Plus a small explicit set of old bed-status and Forge server-message keys.

The following remain owned by ViaVersion + modern Minecraft and must **not** consume the 1.7.10 catalogue:

```text
item.*
ordinary tile.* / block.*
entity.*
container.*
options.*
forge.configgui.*
fml.configgui.*
```

This is a hard regression rule. Nested item/block names inside a preserved outer server message also continue through Via's normal content translation path.

## Language resources

The user supplied original Minecraft/Forge 1.7.10 `en_US.lang` and `zh_TW.lang` files.

Only message-oriented entries are retained as build inputs under:

```text
assets/lfb-minecraft/legacy-lang/en_us/*.lang
assets/lfb-minecraft/legacy-lang/zh_tw/*.lang
assets/lfb-forge/legacy-lang/en_us/*.lang
assets/lfb-forge/legacy-lang/zh_tw/*.lang
```

At build time they are converted to normal modern language JSON resources:

```text
assets/lfb-minecraft/lang/en_us.json
assets/lfb-minecraft/lang/zh_tw.json
assets/lfb-forge/lang/en_us.json
assets/lfb-forge/lang/zh_tw.json
```

Generated keys are collision-free aliases such as:

```text
lfb.minecraft.commands.help.header
lfb.forge.forge.texture.preload.warning
```

Therefore these resources cannot globally replace real 1.21.11 item/block/UI translations.

## alpha.10 runtime failure discovered by live test

The first live alpha.10 startup exposed a failure that compile/test CI did not catch.

ViaFabricPlus 4.4.15 ships ViaVersion with Gson relocated at runtime:

```text
compile/API side:
com.google.gson.JsonObject

live runtime side:
com.viaversion.viaversion.libs.gson.JsonObject
```

`ViaComponentTranslationMixin` had callback parameters typed as `com.google.gson.JsonObject`. The live target method descriptor instead contained Via's relocated Gson class, so Mixin rejected the injection before gameplay startup.

Observed failure:

```text
InvalidInjectionException
Expected (...;Lcom/viaversion/viaversion/libs/gson/JsonObject;...)V
but found (...;Lcom/google/gson/JsonObject;...)V
```

This is not a CustomSkinLoader or graphics issue. It is an LFB Mixin descriptor mismatch.

## alpha.11 fix

The JSON Mixin boundary is now relocation-neutral:

```text
ViaComponentTranslationMixin JSON callback parameter
→ @Coerce Object
→ ViaJsonObjectAccess
→ reflection over the stable Gson-compatible methods:
   get(String)
   getAsString()
   addProperty(String, String)
```

The callback descriptor no longer contains either Gson package. It can therefore match the API-side unshaded class during compilation and the ViaFabricPlus runtime-relocated class during live Mixin application.

A regression test inspects the compiled Mixin bytecode and requires:

- JSON callbacks contain `java.lang.Object` for the JSON object parameter;
- no `com/google/gson/*` descriptor appears;
- no `com/viaversion/viaversion/libs/gson/*` descriptor is hard-coded;
- the JSON object parameter carries `@Coerce`.

A separate adapter test validates the reflective JSON access contract with a Gson-compatible `JsonObject`.

## Development / CI workflow guardrail

See [`DEVELOPMENT-WORKFLOW.md`](DEVELOPMENT-WORKFLOW.md).

The required sequence is now:

```text
create branch
→ research/inspect first
→ prepare all code/tests/resources/docs
→ batch related files
→ move branch head
→ only then open PR
→ one PR CI
→ runtime smoke test when Mixin/runtime-sensitive
→ merge
→ one main CI
```

Do not open a PR while still assembling many small files. The previous alpha.10 language import created many PR synchronizations and redundant queued workflow runs even though `cancel-in-progress` was enabled.

For multi-file GitHub changes, prefer:

```text
create_blob × N
→ create_tree once
→ create_commit once
→ update_ref once
```

rather than many sequential `create_file` / `update_file` commits on an already-open PR.

## Guardrails

- Keep `FML|HS` handshake and `FML` runtime codecs separate.
- Do not assume modern registry raw IDs equal Forge 1.7.10 numeric IDs.
- Do not globally mutate modern registries or the modern Minecraft language table.
- Do not translate `EntityAdjustMessage` into direct entity teleportation.
- Do not intercept or replace player skin resolution in LegacyForgeBridge.
- Do not reverse-match Via's English strings back into translation keys.
- Preserve only legacy **message** translation keys; do not route item/block/entity/container names through the 1.7.10 catalogue.
- Do not bind Mixin callback descriptors to dependency classes that ViaFabricPlus may relocate/shade at runtime.
- Keep `legacyforgebridge.log` as one file per Minecraft launch.
