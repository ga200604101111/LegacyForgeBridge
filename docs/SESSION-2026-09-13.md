## What fixed the handshake timeout

The old Fabric CONFIGURATION sender was not sufficient for the Forge 1.7.10 serverbound handshake path.

`alpha.6` uses a direct ViaVersion serverbound PLAY-pipeline transport:

```text
LegacyForgeBridge FML state machine
→ ViaVersion UserConnection
→ Serverbound CUSTOM_PAYLOAD
→ Protocol1_12_2To1_13
→ channel alias reverse mapping
→ FML|HS / REGISTER
→ legacy 1.7.10 server
```

Inbound Forge packets remain received through the translated Fabric CONFIGURATION / PLAY payload receivers.

## alpha.7 — Forge/FML runtime bridge

`alpha.7` implements the first Forge 1.7.10 runtime layer without modifying the already-working `FML|HS` handshake state machine.

### Dedicated runtime codec

Added `FmlRuntimeCodec` for the legacy `FML` runtime channel. It is intentionally separate from `FmlWireCodec`, because the discriminator values overlap but mean different things.

Correct Forge 1.7.10 runtime discriminators:

```text
0 = CompleteHandshake
1 = OpenGui
2 = EntitySpawnMessage
3 = EntityAdjustMessage
```

`legacyforgebridge.log` now resolves discriminator names by channel, so runtime `FML` discriminator `0x03` is logged as `EntityAdjustMessage` instead of the handshake-only `ModIdData` name.

### Runtime dispatcher

Added `FmlRuntimeClient` and connected it to both mapped CONFIGURATION and PLAY `FML` receivers.

Current behavior:

- `CompleteHandshake`: decoded and accepted; no legacy NetworkDispatcher queue is reproduced because translated packets are already delivered in order by the modern stack.
- `OpenGui`: fully decodes `windowId`, `modId`, `modGuiId`, `x`, `y`, `z`; converted-mod GUI dispatch remains future work.
- `EntitySpawnMessage`: decodes the stable entity header (`entityId`, mod identity/type, fixed-point position, yaw/pitch/head yaw). The legacy DataWatcher / throwable / mod-specific tail remains intentionally opaque until the converted-mod entity bridge exists.
- `EntityAdjustMessage`: decoded and applied during PLAY.

### EntityAdjust semantic bridge

Forge 1.7.10 does not teleport the entity when receiving `EntityAdjustMessage`.

The original behavior is:

```text
entity.serverPosX = message.serverX
entity.serverPosY = message.serverY
entity.serverPosZ = message.serverZ
```

Those values are 1/32-block fixed-point coordinates and form the baseline used by later relative entity movement packets.

Minecraft 1.21.11 stores the equivalent concept in the entity packet-position `VecDeltaCodec`, so `alpha.7` maps it as:

```text
serverX / 32.0
serverY / 32.0
serverZ / 32.0
    ↓
Entity.syncPacketPositionCodec(x, y, z)
```

It deliberately does **not** call `setPos`, `snapTo`, teleport APIs, or otherwise move the rendered entity directly.

If the entity does not yet exist client-side, the packet is logged and skipped rather than fabricating an entity.

## Remaining issues

### 1. Player/entity visual parity

The previously reported own-player appearance problem still needs live diagnosis after `EntityAdjustMessage` is active.

Keep these causes separate:

- entity position / interpolation / rotation behavior;
- skin/model behavior (Steve/Alex arm width, skin layers, cape, texture/profile properties).

If `alpha.7` fixes positional/interpolation oddities but the model still looks wrong, move directly to profile/skin/model conversion diagnostics instead of changing movement handling again.

### 2. Full modded EntitySpawn behavior is not implemented

`EntitySpawnMessage` parsing currently stops after the stable header.

Future modded entity support must handle:

- legacy DataWatcher metadata;
- Forge entity registration lookup;
- converted mod entity identity;
- throwable owner / velocity fields;
- `IEntityAdditionalSpawnData` equivalent payload dispatch.

Do not implement this by assuming modern raw entity registry IDs equal Forge 1.7.10 IDs.

### 3. Legacy OpenGui dispatch is not implemented

The packet is now parsed correctly, but opening the converted modern GUI requires the mod conversion/identity layer first.

### 4. Legacy chat / translation keys can appear in English

Observed examples include old 1.7.10-era messages such as achievement and game-mode messages.

Likely cause: modern 1.21.11 no longer contains some legacy translation keys / old achievement-system keys, so translated components can fall back to English or lose their old localized text.

Need a session-only legacy translation fallback, not a global replacement of the modern language table.

## Important guardrails

- Vanilla 1.7.10 protocol translation remains ViaFabricPlus/ViaVersion responsibility.
- LegacyForgeBridge owns Forge/FML behavior, registry identity, converted mod compatibility and legacy runtime semantics.
- Keep handshake (`FML|HS`) and runtime (`FML`) codecs separate.
- Do not assume modern raw registry IDs equal Forge 1.7.10 numeric IDs.
- Do not globally mutate the modern Minecraft registry or language tables.
- Do not translate `EntityAdjustMessage` into a direct teleport; it is a relative-movement baseline update.
- Keep `legacyforgebridge.log` as one file per Minecraft launch, truncated on startup.
- Continue using direct ViaVersion transport for Forge/FML serverbound handshake/runtime packets when required by legacy PLAY semantics.
