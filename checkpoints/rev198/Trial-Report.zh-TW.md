**不是只有幾把普通劍的包，不能把整體判定為簡單。** 方塊／物品身分部分較適合先做；實體、武器操作和模型仍有實質缺口。部分實體註冊受設定控制，上表不能直接解讀成任何伺服器都一定啟用 54 種實體。沒有宣告前置、沒有檢出 CoreMod 也不等於已證明所有可能相依情況。

武器／投射物群的註冊使用靜態計數器；生物輔助方法使用 `EntityRegistry.findGlobalUniqueEntityId()`，再把動態取得的數字傳給 `registerModEntity`。後者會受到設定、順序與其他模組共用 ID 分配環境影響，不能寫死數字或從類別名猜。現有分析器還不能完整還原這段流程。

## 本次實際修改

### 共用方塊名稱資料流

rev197 漏讀四個方塊，原因是來源以 `getUnlocalizedName().substring(5)` 取出註冊名。原分析器有處理物品路徑，沒有等價地證明方塊路徑。

rev198 分開追蹤 Block 的 `tile.*` 與 Item 的 `item.*` 名稱，支援已確認的原版 MCP／SRG 方法、字面值名稱／常數欄位、受限的鏈式設定、靜態欄位與 helper 參數傳遞。覆寫方法、未知繼承、未知副作用、非定值 substring 參數或可能來自未知來源的名稱仍拒絕。

結果由 99 物品、0 方塊改為 **99 物品、4 方塊、103 個欄位綁定**。修正程式沒有 `iymts_mod`、Bamboo 名稱或原始 JAR 雜湊的特判；任意名稱、相同可證明結構均可使用。這仍不是任意 Java 程式的完整執行分析，reference locals 等路徑尚未全面支援。

### 共用建構參數型別檢查

實際生成流程發現，材質物件被用可讀字串形式帶入生成建構式，JVM 會拒絕 `String` 傳入需要 `Material` 的位置。舊版負對照已重現 `VerifyError`。

rev198 在接受綁定前檢查完整建構式描述符、參數數量及可生成的實際 JVM 常數型別。不支援的物件／材質參數會針對該綁定明確拒絕，其他可處理項目仍繼續。沒有偽造材質、任意補 null 或吞掉 JVM 錯誤。

**這項修正代表不再生成那種非法建構呼叫，不代表相關裝備材質與武器功能已全部實作。**

## 首輪試轉到底到了哪裡？

完整發行版轉換引擎在本地因缺少 Mojang `Codec` 宿主相依而中止，這是目前建構環境的限制，不能歸罪於模組本身。

另建立明確標為 diagnostic-only 的試跑器，讀取實際發行版的轉換計畫，105 個步驟只略過需要該宿主的 `LegacyRecipeMaterializationPass`。其餘 **104 個步驟完成呼叫**，強制標示 `installable=false`，不打包候選模組。

試跑結果為：

- 99 個獨立物品與 4 方塊的基本身分已產出；但 **103 個模型身分仍未解析，來源證明的預設圖示為 0**。
- **54 個實體註冊候選全部被跳過，實際接通的實體規則為 0**。
- 產出 19 個行為／身分綁定，但它們不是 19 個已通過實機驗收的完整物品。

完成 104 個步驟不等於完成 104 種功能，很多步驟的結果是沒有匹配規則或列出不支援事項。沒有拿佔位模型或單純的 FML 身分宣告當成成功轉換。

圖示缺口還包括：來源物品欄位在生命週期 helper 中分配，現有圖示分析器沒有充分連結這些分配與建構式參數。下一步應擴充共用分配／貼圖來源追蹤，再做實體註冊、同步欄位、模型與操作，而不是依檔名直接猜材質。

## 驗證

完成 74 項方塊名稱斷言（40 個正負案例）與 27 項建構參數斷言，共 **101 項新斷言**。舊版 String→Material 錯誤可重現，新版拒絕錯誤綁定並保留另一個合法綁定。

針對實際發行 JAR 驗證：36 個基準類別的正規化位元碼與 rev197 相同；29 個修改／新增類別通過純 Java 的 JVM 驗證，另有 255 個 ASM BasicVerifier 方法；保留 128 個可見成員，1,446 個既有 JAR 條目內容不變。三個修改來源檔使用真正的 ASM／Gson 與既有橋接 API 編譯，未使用 Minecraft 編譯替身。

原始 Bamboo 的登錄及行為分析與修改前一致：100 登錄、99 欄位綁定、87 物品行為、3 事件綁定，40 個生成行為類別內容逐位元組一致。沒有重新做完整 Bamboo 進服測試，也沒有新跑 RPGTool1 原始樣本回歸。

獨立目錄重建，以及從壓縮 payload 驗證／套用後的來源重建，均得到同一 JAR。已驗證三個來源檔與八個建構／測試來源的還原內容；沒有在本次重新跑完整 rev189–198 checkpoint 鏈。

**沒有完整 Gradle／Loom 建構、Minecraft／Fabric／Mixin 啟動或真實伺服器驗收。** 純 Java 驗證不能保證渲染、操作和網路同步正常。沒有要求 GitHub Actions 建構。

## 使用與來源保存

正常遊玩先保留已測的 rev197。新主模組檔案 `legacyforgebridge-0.2.0-alpha.27-rev198-experimental.jar` 僅是開發／試轉版本，SHA-256：`0208f6d22e19875bbbff52d8d65fef2ebfb455866fff548ba72b64f4cf31cdb9`。

GitHub 根目錄 `src/` 尚未展開所有累積修改，來源仍透過 checkpoints 保存。完整來源需在新目錄還原：

```sh
python checkpoints/rev198/restore.py --output ../LegacyForgeBridge-rev198
```

原始附件、第三方反編譯來源與相依 JAR 不上傳到專案；只保存橋接器修改、樣本雜湊、可重跑工具與分析結果。目標仍是新版客戶端相容原始 1.7.10 伺服器，AI、傷害與世界生成不在客戶端重做，但客戶端所需的實體／模型／同步不能省略。
